# ע — Exported-origin continuation

Status: validated spec, registry, runtime, tests, and trace notes are aligned.

## Definition

- **Select:** current focus (`F`).
- **Bound:**
  1. let `s := F` (snapshot origin).
  2. allocate successor (`F⁺ := alloc()`).
  3. add `cont(s, F⁺)`.
  4. add `carry(s, F⁺)`.
  5. allocate origin handle (`h := handle_to(s)`).
- **Seal:** push `h` to `K`; set `F := F⁺`.
- **Key distinction:** edge set is identical to `נ`; the only operator-level difference is that `ע` exports the origin while `נ` does not.

## Signature

- Arity: req 1, opt 0.
- Operand kinds: any.
- Selection precedence: default (see `spec/60-VM.md`).
- Distinctness/reflexive: default (see `registry/letters.yaml`).
- Obligations: none opened, none closed.

## Validation Chain

- Sources consulted:
  - `Shabbat 104a`: `ס"ע = סמוך עניים`, used as the mechanical check that `ס` should resolve the nearest unresolved `ע` carry.
  - `אותיות דרבי עקיבא`, Version A: `עין` read as a perception channel.
  - `אותיות דרבי עקיבא`, Version B: `עון` read through rejection/failure.
  - `Keset HaSofer`, Chapter 5: scribal shape constraints used as morphology input, not as direct runtime semantics.
- Architectural extraction:
  - `ע` uses the same edge primitives as `נ`: `cont` plus unresolved `carry`.
  - The one semantic parameter change is export destination: `ע` exports an origin handle to `K`.
- Rejected interpretations:
  - `persistent watch-handle` as the semantic label.
  - zero-edge handle export from the CG proposal, because it breaks the `ס`/`ע` pairing by leaving nothing for `ס` to resolve.
  - full `ז` import, because scribal notes that `ע` is "like zayin" do not justify assigning operator `ז` semantics to `ע`.
- Open question:
  - whether carry-linked handle staleness should be enforced as an explicit VM rule or remain emergent from `eff()` changing status after resolution.
- Confirmatory note:
  - milui `עי״ן` remains supportive rather than determinative: export-origin (`ע`) -> pin (`י`) -> commit-lock (`ן`).
